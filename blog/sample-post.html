Why I Switched to a Framework-Free Website

June 15, 2026 · 5 min read

For the past three years, my personal website ran on Jekyll — a static site generator that takes Markdown files and turns them into HTML. In theory, it was perfect: I could write blog posts in a simple text format and let the tool handle the messy details. In practice, it was a recurring headache.

The problem with dependencies

Every few months, I'd try to update my site and discover that something had broken. Ruby version conflicts, deprecated gems, build errors that produced cryptic messages. It felt like owning a car that needed a different kind of gasoline every season — the engine was fine, but the fuel supply chain kept changing underneath me.

The best technology is the kind you can forget about. If your website tooling demands attention when you're trying to focus on content, the tooling is working against you.

This isn't unique to Jekyll. Hugo, Gatsby, Next.js — every framework introduces a layer of indirection between what you write and what appears on screen. That layer has its own update cycle, its own breaking changes, its own community churn. For a complex web application, the trade-off is worth it. For an academic personal site with five pages, it's overhead with no payoff.

What I did instead

I rewrote everything in plain HTML and CSS. No build step, no package manager, no node_modules folder. The entire site is a handful of .html files and one style.css.

Modern CSS is remarkably powerful. Features like flexbox, grid, custom properties (variables), and media queries handle responsive layouts, theming, and component-like styling without any JavaScript framework. The dark mode toggle on this site is 15 lines of vanilla JS.

The benefits

  • Zero maintenance: HTML and CSS don't have version conflicts. A page written today will render identically in 2036.
  • Instant builds: There's no build step. I edit a file, push to GitHub, and it's live in seconds.
  • Full understanding: I can read and modify every line of my site. Nothing is hidden inside a framework's abstractions.
  • Speed: No JavaScript bundle to download. The site loads in under 200ms on a slow connection.

The trade-off

The main cost is repetition. The navigation bar is copy-pasted across every page. If I add a new nav link, I update it in five files. For a site this small, that takes about 30 seconds. For a site with 200 pages, I'd want a different approach — but academic sites rarely have that many pages.

Blog posts require writing HTML instead of Markdown. But HTML for prose is simple: <p> for paragraphs, <h2> for headings, <a> for links. Once you know five tags, you know enough.

Should you do this?

If you're an academic maintaining a personal site and you've been frustrated by framework churn, I'd strongly recommend trying plain HTML. It's less glamorous than the latest React-based static site generator, but glamour isn't what you need. You need something that works reliably while you focus on research.

If you'd like to use this site as a starting point for your own, the source is on GitHub. Fork it, replace my name with yours, and you're done.
